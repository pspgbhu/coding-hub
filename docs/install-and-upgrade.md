# 安装、首次使用与升级

本文对应当前 0.1.1 代码。默认产物是内部测试构建；生产签名、公证、更新源和各目标系统的安装验收仍需分别提供证据，见[验证记录](verification.md)。

## 运行条件

| 用途           | 条件                                                                                                     |
| -------------- | -------------------------------------------------------------------------------------------------------- |
| 运行已打包应用 | macOS x64 / arm64 或原生 Windows x64；本机 Git；至少一个可用的 Agent CLI。应用本身包含 Electron 运行时。 |
| 从源码开发     | Node.js 24、pnpm 11.24.0、Git，以及对应 CLI 的运行环境。                                                 |
| Agent 登录     | 在对应官方 CLI 中完成安装、账号登录、订阅 / API 配置；Coding Hub 不接管凭据。                            |

当前 CLI 最低版本为 Claude Code 2.1.236、Codex CLI 0.151.0、OpenCode 1.19.5。新版 CLI 仍可能发生协议变化；检测结果和实际执行错误比版本号更能说明当前连接状态。

本次实测宿主为 macOS x64。macOS arm64 和原生 Windows x64 已有 CI 配置，尚不能据此宣布目标机器安装、升级和卸载已通过。

## 安装应用或从源码启动

维护者提供 macOS 的 DMG / ZIP 或 Windows 的 NSIS 安装包时，先核对其版本、目标架构和随包的 `SHA256SUMS.txt`。macOS 将应用安装到应用目录；Windows 按 NSIS 向导选择目录与快捷方式。内部未签名包可能被系统或组织策略拦截，外部分发前需要完成正式签名及验收。

没有可用安装包时，从源码启动：

```sh
pnpm install --frozen-lockfile
pnpm dev
```

独立测试数据目录可在启动前设置，避免与日常会话混用。

macOS / zsh：

```sh
CODING_HUB_USER_DATA="$HOME/.coding-hub-dev" pnpm dev
```

Windows / PowerShell：

```powershell
$env:CODING_HUB_USER_DATA = Join-Path $env:LOCALAPPDATA 'coding-hub-dev'
pnpm dev
```

该变量只改变 Coding Hub 数据目录，不隔离或重置原 CLI 的账号配置。不要把测试会话、凭据或数据目录提交到仓库。

## 第一次完成任务

1. 打开项目目录。需要新项目时使用创建或克隆入口；克隆地址使用不含密码 / token 的 HTTPS 或 SSH 地址。
2. 查看项目后确认信任。受限模式允许浏览；编辑、Git、Agent、终端和检查需要明确信任。
3. 打开「设置 → Agent 连接」。自动检测不到版本管理器或自定义安装位置时，填写可执行文件完整路径，保存并重新检测。
4. 检查安装、协议版本、账号与模型四项状态。账号显示“未验证”时，先在原 CLI 里验证登录；获取模型列表成功也不保证账号可使用其中每个模型。
5. 新建会话，选择 Agent 和模型。可选择“使用 CLI 配置”，否则以创建时展示的模型为准。
6. 有 Git HEAD 的项目默认使用新 worktree；非 Git 或未建立首个提交的项目使用共享目录。也可明确选择已有工作区。
7. 先执行可核对的小任务，例如解释入口或检查当前状态。授权卡片允许同意、拒绝或回答；停止失败时应先恢复停止状态，再启动新的工作。
8. 查看本轮变更，明确运行所需检查，再到代码工作区审阅已暂存内容、提交并推送。检查面板发现 `package.json` scripts，支持 pnpm / npm / yarn / bun；其他构建系统可在终端明确运行。

独立 worktree 只包含选定提交中的内容。原目录未提交的修改、`.env` / `node_modules` 等被忽略内容不会额外复制；依赖安装与检查脚本由你明确发起。既有 native session 不会迁移到新 cwd。

代码工作区支持快速打开、内容搜索、编辑、保存全部及外部编辑器。内置编辑上限为 2 MB UTF-8 文本；二进制或大文件可保留在 Git 变更列表中交付，文本预览会说明限制。文件删除是**永久删除**，界面会单独确认。

## 日常关闭与重新打开

关闭窗口会隐藏到托盘，后台任务与终端可继续运行。需要退出时使用应用菜单或托盘中的退出入口。重启后会恢复已保存的会话、草稿与编辑缓冲区；已中断任务不会自动重发，终端进程也不能跨应用退出继续运行。

重新连接原生会话还依赖 CLI 自己的历史和配置。更换机器、清除 CLI 数据或模型权限变化可能使旧 native session 无法继续；新建会话时，原聊天记录仍可保留和导出。

## 手动升级

1. 保存重要源码、提交需要保留的 worktree 修改，并在「设置 → 数据与备份」创建手动备份。
2. 停止 Agent 和检查，结束不再需要的终端，从应用菜单退出。
3. 安装同一应用标识的新版本，保留原数据目录。首次启动会检查数据完整性，并在需要迁移时创建升级前快照。
4. 核对项目、会话、草稿、编辑缓冲区和原 CLI 路径，再开始新任务。

应用内备份由 SQLite 快照和同名 `.outputs` 附件目录组成，迁移时需一起保留；它不包含项目文件或 CLI 账号目录。完整边界见[数据与恢复](data-and-recovery.md)。不要用旧版程序直接打开已升级的数据。需要回退时，保留当前数据，并先在独立数据目录验证旧版与对应升级前备份。

## 应用内更新

只有打包应用包含有效更新配置时，设置中的更新入口才会检查 feed。默认内部构建显示未配置；不会凭空获得正式更新服务。

更新按“检查 → 下载 → 明确重启安装”进行，不自动下载或在普通退出时安装。安装前需要处理运行任务、终端和未保存文件。更新失败时保留当前版本，查看诊断并重新检查；生产升级成功与失败场景仍需发行验收，见[发行指南](releasing.md)。

## 卸载与数据保留

卸载应用与删除用户数据是两件事。先保留数据库备份、重要输出和项目源码；尤其检查由 Coding Hub 创建在数据目录下的 worktree，其中可能仍有未提交代码。

应用安装器、系统卸载入口及组织策略对残留数据的处理可能不同。不要把删除整个数据目录当成普通重装步骤。需要完整清理时，先按[数据目录说明](data-and-recovery.md)核对所有仍需保留的内容。
